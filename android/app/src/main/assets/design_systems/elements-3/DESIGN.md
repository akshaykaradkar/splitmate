# Elements GM3 Design System

## Overview

Elements GM3 is the next-generation enterprise design system created by Google’s Corp Eng team. Designed to align directly with the Google Material 3 (GM3) framework, Elements GM3 bridges the gap between high-level brand expression and the rigorous density, complexity, and accessibility requirements of internal Google applications (such as Wiz, ACX, and Angular).

In Elements GM3, the visual interface is modern, clean, friendly, and deeply "Googley." It prioritizes simple and direct interactions, using clear content hierarchies and strategic visual anchors to guide attention. The core design principles are:

1. **Focus on the User:** Understand and empathize with user workflows, delivering useful experiences in the moments that matter.
2. **Build for Everyone:** Emphasize deliberate, universal accessibility, honoring every voice and viewpoint, and satisfying rigorous Google Accessibility Ratings (GAR) standards.
3. **Keep it Simple:** Base designs on simplicity, clarity, and focus, only adding elements that actively serve the user's intent.

## Colors

The Elements GM3 color system relies on Material 3's tonal roles for contextual branding, while keeping the main utility and semantic surfaces intact to prevent cognitive fatigue or overwhelming saturation.

### Theming Strategy

Elements GM3 provides seven distinct theme colorways. To maintain predictability and high-contrast navigation across different applications, product sections, and user roles (e.g., manager views versus standard employee profiles), only the **primary** and **secondary** color moments migrate to these local themed roles. The following surfaces remain in their default neutral states regardless of theme:

- Default surface and container backgrounds
- Default on-surface text and icon colors
- Default outlines and outline variants
- Default link colors
- Default semantic colors

Red is strictly excluded as a brand theme color because it is reserved exclusively for error states and critical negative semantic indicators.

### Pre-defined Theme Colorways

- **Baseline (Blue):** The standard theme for Corp Eng products, aligning with Google's core identity. Features `{colors.extended-blue}` as the primary driver and `{colors.extended-blue-container}` for tonal containers.
- **Cyan:** Often utilized for sections relating to metrics or performance tracking (e.g., primary `{colors.extended-cyan}`).
- **Orange:** Uses `{colors.extended-orange}`. Because orange themes feature lower default contrast on light surfaces, they are "reversed" on dark mode and require manual adjustment to meet WCAG AA contrast standards.
- **Yellow:** Uses `{colors.extended-yellow}`. Like orange, yellow themes are reversed and require meticulous manual contrast verification. Informational callouts should avoid yellow or orange accents to prevent styling conflicts.
- **Green:** Frequently applied to sections representing career progression, success metrics, or growth (e.g., `{colors.extended-green}`).
- **Pink:** Adds playfulness or reinforces branding for distinct internal services (such as "Eat"), using `{colors.extended-pink}`.
- **Purple:** Reserved for compensation or financial sections (e.g., `{colors.extended-purple}`).

### Semantic and Utility Colors

To ensure a predictable, highly visible experience, semantic and interaction colors stay consistent across all themes:

- **Success:** Commits to `{colors.extended-success}` and `{colors.extended-success-container}`.
- **Warning / Caution:** Uses `{colors.extended-warning}` and `{colors.extended-warning-container}` to indicate warnings without the severity of red.
- **Error:** Uses `{colors.extended-red}` and `{colors.extended-red-container}`. Trailing error icons in fields must be error-colored to ensure colorblind users can perceive the state.
- **Information:** Employs `{colors.extended-info}` and `{colors.extended-info-container}`.
- **Links:** Hyperlinked inline text must be underlined and use `{colors.extended-link}` (default), `{colors.extended-link-hover}` (hover), or `{colors.extended-link-visited}` / `{colors.extended-link-visited-hover}` (visited states) to communicate distinct contextual states.

### Contrast Ratios and Accessibility

All user experiences must adhere to WCAG and GAR requirements:

- **Normal Text (below 18pt regular/medium):** Must maintain a contrast ratio of at least **4.5:1** against the background.
- **Large Text (14pt bold, 18pt regular and larger):** Must maintain a contrast ratio of at least **3:1** against the background.
- **Google Sans Exception:** Since Google Sans is a wide font, any medium weight text at 16pt and above is considered large text and only requires a **3:1** contrast ratio.
- **Non-Text Contrast (NTC):** Outlines for interactive components like chips and text fields have been made systematically darker in Elements GM3 (using tokens like `{colors.extended-grey-outline}`) to comply with NTC guidelines.

### AI Gradients

To represent fluidity and advanced intelligence, Elements GM3 employs subtle color gradients.

- For products with a single reinforced brand identity, the gradient can be customized to match the brand colorway.
- For multi-themed products that segment views by sections or roles, developers must use the default CE AI gradient to avoid user confusion.

## Typography

Typography in Elements GM3 acts as the primary driver of information hierarchy. By moving away from GM2's hardcoded styles, GM3 introduces a role-based typesetting strategy.

### Typeface Strategy

To project Google's internal identity while maintaining optimal legibility at all scales, the system splits typographic duties between two families:

1. **Google Sans:** Google's proprietary typeface, used exclusively for large, high-emphasis text. It is assigned to **Display**, **Headline**, and **Title** roles at sizes **18 and up**.
2. **Google Sans Text (GST):** An optimized, highly readable version of Google Sans. Featuring adjusted letter spacing and open counters, GST is used for **Body**, **Label**, and small text roles at sizes **17 and below**, as well as any long-form reading blocks.

### Static Font Theme and Baseline Scales

To enforce consistent reading experiences, Elements GM3 requires the use of the **Static font theme** over variable axes (e.g., Google Sans Flex) and mandates the **Baseline type scale** instead of the Emphasized scale. Emphasized scales, which feature increased weights and 100% roundedness, are strictly reserved as built-in selected indicators within system components.

### The Five Typographic Roles

- **Display (`typography.display-large-link`, `typography.display-medium-link`, `typography.display-small-link`):** The largest text on the screen, reserved for critical short phrases or prominent numbers. Best used on large, spacious viewports.
- **Headline (`typography.headline-large-link`, `typography.headline-medium-link`, `typography.headline-small-link`):** Best suited for high-emphasis, short region markers or titles.
- **Title (`typography.title-large-link`, `typography.title-medium-link`, `typography.title-small-link`):** Smaller than headlines, titles segment secondary content blocks or section titles.
- **Body (`typography.body-large-link`, `typography.body-medium-link`, `typography.body-small-link`):** Set in GST, optimized for long paragraphs. Comfortably keep line lengths between **40 and 60 characters** (maximum 80 for WCAG AAA compliance). On desktop views with wider blocks (up to 120 characters), line-heights must increase from 20pt to 24pt to ensure readability. Never justify text.
- **Label (`typography.label-large-link`, `typography.label-medium-link`, `typography.label-small-link`):** Small, utilitarian styles for component labels (like buttons) or captions.

### Typographic Layout Rules

- **The 4dp Grid:** Regardless of size or viewport, every text element's baseline must sit on the **4dp vertical grid**. Line heights must always be a value divisible by 4 to preserve this vertical rhythm.
- **Limit Bold Formatting:** Bold weights are intended strictly for inline emphasis within long strings of body text. Bold must not be used as a default shortcut for headlines or section titles; use the appropriate Title role instead.
- **Tabular Numbers:** Always use tabular (monospaced) numbers in data tables, status clocks, or rapidly changing counters to ensure numeric columns remain optically aligned.
- **Text Spacing and Resizing (GAR 2024):** All text elements must scale up to **200%** without clipping, overlapping, or truncating. Containers must either dynamically expand in height, wrap text to multiple lines, or provide keyboard-accessible tooltips on focus to expose full content.

## Layout

Elements GM3 enforces a shared, responsive page structure that establishes visual consistency across all Google products.

### Layout Anatomy

The default layout consists of four key regions:

1. **App Bar:** A standardized global header that surfaces branding, search, user profiles, and global support actions.
2. **Navigation Drawer / Rail:** Standard vertical navigation. A 12-column drawer is visible on desktop, whereas a collapsed rail or modal drawer is used on smaller viewports.
3. **Main Body:** The primary workspace. Uses a maximum width of **840dp (Narrow Layout)** for content-focused layouts (lists, cards, forms) or **1200dp (Wide Layout)** for complex, data-heavy displays (tables, dashboards).
4. **Standard Side Sheets:** Docked, optional right-hand panels used to surface contextual details without interrupting the parent task.

### Alignment Options

- **Left-Aligned Layout:** Highly recommended for products utilizing wide components like data tables. Features a consistent **24dp margin** between the navigation drawer and the main content, with content left-aligned directly with the App Bar search input.
- **Center-Aligned Layout:** Recommended for narrower, simpler structures like cards or lists. Margins on both sides of the content are equal and fluid.

### Grid Breakpoints and Margins

Responsive behavior shifts dynamically based on viewport widths:

- **Desktop (\>=600dp):** Employs a **12-column grid** with fluid margins starting at a minimum of **24dp**. Gutter widths are fixed at **24dp** when the main body width is \>=840dp, and contract to **16dp** when the body is \<840dp.
- **Mobile (\<600dp):** Employs a **4-column grid** with a minimum margin of **16dp**. Elements must stack into a clean **1-column layout** visually; the 4-column structure is used only to determine interior sizing.

### Inset Padding Rules

To maintain the integrity of the grid system, the application of inset padding is restricted to three distinct use cases:

- **Case A (No separate container color):** Do NOT use inset padding. Align titles, buttons, text fields, and callouts directly with the grid columns. Excess padding inside invisible containers creates dead space and breaks vertical rhythm.
- **Case B \& C (Colored containers or outline strokes):** When content is grouped inside a container that has a distinct fill or outline (such as cards, lists, expansions, or tables), apply a strict **16dp inset padding** to keep elements legible.
- **Case D (One-pane scrolling layout exception):** If the entire main body sits inside a single large, fixed-height pane with a background color different from the page background, apply **24dp inset padding** to match the side sheet visual alignment and provide breathing room.

### Spacing and Interaction Targets

- **Interactive Target Size:** To support users with motor or visual impairments, all interactive targets (buttons, links, icon targets) must maintain a minimum bounding box of **48x48dp**, regardless of visual density, with at least **8dp** of spacing between adjacent targets.
- **Skip Link:** Every page layout must place an invisible "Skip to main content" link as the absolute first keyboard tab stop in the App Bar. Activating the skip link immediately transfers focus to the `<main>` landmark.

## Elevation \& Depth

Elements GM3 moves away from the shadow-heavy surfaces of GM2, adopting a modern, flatter visual hierarchy where elevation is depicted primarily through **Tonal Surface Changes** and color contrast.

### Depicting Elevation Tonalities

Elevation is indicated by changing container fills and outlines, keeping shadows reserved for exceptional moments where physical separation or absolute priority is required. Outlines (width: 1px, color: `outline-variant` or `{colors.extended-grey-outline}`) are preferred for flat groupings on the same plane. Shadows are only applied to protect interactive elements (like buttons or chips) against busy, patterned, or media-rich backgrounds.

### Six Levels of Elevation

- **Level 0 (0dp resting height):** Resting state for standard panels, standard side sheets, dialog containers, date pickers, flat card variants, progress indicators, and standard buttons.
- **Level 1 (1dp resting height):** Resting height for elevated buttons, switch handles, and elevated chip variations. Features minimal, crisp shadows.
- **Level 2 (3dp resting height):** Resting height for elevated cards, dropdown menus, cascaded menus, rich tooltips, and modal navigation rails/drawers appearing above content without scrims.
- **Level 3 (6dp resting height):** Resting height for the active App Bar (during scroll), active global search views, active snackbars, and all FAB sizes (small, medium, large).
- **Level 4 (8dp height):** Reserved exclusively for active interaction states (hover and focus). Components temporarily lift to Level 4 when hovered or focused.
- **Level 5 (12dp height):** Reserved exclusively for pressed or active touch states. Components lift to Level 5 during active pointer compression.

## Shapes

The Elements GM3 shape system uses seven systematically assigned corner styles to define visual hierarchy and group related functions. Corner radii range from square to fully circular.

### Shape Scale and Corner Radii

1. **None (0dp):** Square corners. Used for top app bars, docking side sheets, standard lists, docked navigation drawer/rail containers, progress indicators, banners, search view (full screen), and tabs.
2. **Extra Small (4dp):** Minimal rounding. Used for outlined text fields, snackbars, standard dropdown menus, select/autocomplete menus, and status badges.
3. **Small (8dp):** Used for all chips (except people chips), rich tooltips, and component-level callouts.
4. **Medium (12dp):** Used for elevated/outlined/filled cards and small FABs.
5. **Large (16dp):** Used for navigation drawers, standard FABs, and extended FABs.
6. **Extra Large (28dp):** Used for modal dialogs, bottom sheets (docked), time pickers, and account menus.
7. **Full (Circular / Pill):** Fully rounded. Used for standard buttons, icon buttons, sliders, switch toggles, search bars, and numeric badges. Circular shapes are calculated as exactly **1/2 of the container height**.

### Shape Rules

- **Asymmetrical Shapes:** Shapes are symmetrical unless tagged with a directional modifier (e.g., `top`, `bottom`, `start`, `end`). Asymmetrical shapes are permitted only when indicating direction or origin, such as speech bubbles in chatbots.
- **Optical Roundness:** When nesting rounded elements (e.g., placing media or an illustration inside a rounded card), avoid using the same corner radius for both. To make corners look balanced and prevent optical distortion, calculate the inner radius as:
  $$\\text{Outer Radius} - \\text{Padding} = \\text{Inner Radius}$$
  *(For example: a 12dp card container with 4dp internal padding must feature an 8dp corner radius on its nested media element).*
- **Shape Layering:** Keep shape layering to an absolute minimum. A card with nested items should read as one singular visual affordance, not as separate competing shapes.

## Components

### Buttons

Buttons trigger immediate, final actions and are styled using five distinct visual hierarchies:

1. **Filled (Primary):** The highest visual impact. Reserved for final, unblocking actions that complete a flow (e.g., "Save", "Confirm", "Submit").
2. **Tonal (Secondary):** Used for final actions that complete a flow but with lower visual priority than filled buttons.
3. **Outlined:** Standard secondary choice, indicating actions that allow users to change their mind or escape a flow (e.g., "Cancel", "Back").
4. **Text (Tertiary):** Lowest priority, text-only buttons. Must be used with caution because their lack of container outlines can cause discoverability challenges.
5. **Elevated:** Tonal buttons with subtle shadows, used only to separate action controls from visually busy or patterned backgrounds.

#### Button Styling and Behaviors

- **Sizing:** Default height is **40dp** with a **48dp touch target**.
- **Typography:** Labels must use sentence case (never ALL CAPS).
- **Icons:** Standard button icons must be sized to **18x18dp** and positioned to the left of the text label. Icon and label text must share the same color.
- **Disabled Buttons Caution:** Hard-disabled buttons are removed from the keyboard tab sequence, making them invisible to screen readers and causing users to get stuck. Elements GM3 strongly recommends keeping buttons fully enabled: if required fields are missing, clicking the enabled submit button should return descriptive, focusable validation errors.
- **Loading State:** Short activities (2-5 seconds) can display a circular progress spinner inside the button, disabling interaction until resolved.
- **Button Placement:**
  - *Bottom-Left Alignment:* For wide components (forms, large dialogs, cards, expansions). Place the **Primary** action on the left, and the **Cancel/Secondary** actions to the right.
  - *Bottom-Right Alignment:* For narrow, task-focused dialogs or feature highlights. Place the **Primary** action on the right, and the **Cancel/Secondary** actions to the left.
  - *Both Sides:* Horizontal steppers place "Back" aligned left and "Next/Submit" aligned right to match the left-to-right reading path.
- **Spacing:** Paired buttons must be separated by exactly **8px** of horizontal spacing.

### Chips

Chips represent multiple, dynamically generated, or reactive interactive elements appearing together in the same area. Unlike buttons, chips represent contextual choices or paths. All standard chips use a **8dp rounded corner** (except Google-specific People Chips, which have circular corners).

1. **Input Chips:** Represent user-authored, discrete pieces of info (e.g., email contacts in a "To" field). Must include a visible trailing "X" delete icon.
2. **Assistive Chips:** Automate multi-step intents. Labels always start with a verb (e.g., "Add to calendar").
3. **Suggestive Chips:** Dynamically generated, product-authored options (nouns/categories) used to narrow user intent.
4. **Filter Chips:** Act as on/off toggles or dropdowns. Elements GM3 filter chips feature darker outlines than default M3 specs to meet Non-Text Contrast (NTC) requirements.

#### Chip Usability Guidelines

- **Text Length:** Keep chip labels under **20 characters**. Truncate longer strings with an ellipsis and expose the full string via a focusable tooltip.
- **Split Chips:** Feature two interactive zones (e.g., a link to a profile on the left, and an "X" delete action on the right). Split chips require expanded interaction targets beyond visual bounds to maintain usability, and should be used sparingly to avoid lengthy keyboard traversal.
- **Accessibility Labels:** When a chip contains a delete function, its accessibility label must be set to `Remove [label text]` (e.g., "Remove John Doe").
- **Group Containers:** When grouping 3 or more chips, the container must be a single tab stop. Use one of three ARIA patterns:
  - *Listbox:* For related on/off filter toggles. Users navigate between chips using arrow keys.
  - *Toolbar:* For filter rows that control content below (like data tables).
  - *Grid:* For arrays of input chips, allowing bidirectional arrow key navigation.

### Input Fields (Text Fields)

Input fields let users enter and edit text.

- **Outlined Text Fields:** The mandatory recommendation for Elements GM3.
- **Filled Text Fields:** Strictly avoided due to accessibility and contrast concerns.
- **Sizing Specs:** Standard height is **56dp** (excluding helper text). Touch targets must be at least **48x48dp**. Vertical spacing between borders of stacked inputs must be exactly **36dp**. Horizontal padding inside the field is **16dp**. A maximum width of **512dp** is recommended for readable line lengths.
- **Dense Text Fields:** Heights can contract to **40dp** (density -4) for dense, data-entry heavy desktop views. Avoid dense inputs on touch-based or mobile interfaces.
- **Required Fields:** Indicated by displaying a red asterisk (`*`) next to the label. The asterisk is colored red only when the field is empty and focused. If most fields are required, label optional fields as `(optional)` in parentheses.
- **Error States:** Invalid fields are indicated by `{colors.extended-red}` outlines (width: 1dp if resting, 2dp if focused), red text, red helper text, and a trailing red error icon (supporting colorblind users). Errors must be accompanied by contextual helper text that explains how to recover.
- **Placeholder Text:** Avoid using placeholder text as a replacement for labels, as placeholders disappear during typing and degrade cognitive usability.

### Dialogs

Dialogs are highly disruptive modal windows that appear in front of primary content to prompt critical decisions.

- **Anatomy:** Comprises a container (fill: `surface-container-high`, shape: Extra Large 28dp), a fixed header, a vertically scrollable body (horizontal scrolling is prohibited), and a fixed footer with actions.
- **Dividers:** 1px horizontal dividers (color: `{colors.extended-grey-outline}` or `outline-variant`) appear between the header/body and body/footer only when body content is scrolled.
- **Size Constraints:** Default width is **560dp** (minimum 280dp, maximum 712dp), restricted by a **72dp margin** from the screen edge.
- **Dismissibility:** Modal dialogs must include a visible, keyboard-focusable dismiss button (like an "X" in the header or a cancel button) and close instantly on pressing the "Escape" key.
- **Initial Focus management:**
  - *Interaction/Form Dialog:* Place initial focus on the first input or actionable element.
  - *Routine Task Dialog:* Focus the most frequently used or positive button in the footer.
  - *Deletion / Destructive Dialog:* Initial focus must be placed on the **dialog heading** (or the container itself if no heading exists) to prevent accidental double-click submission of an irreversible action.

## Do's and Don'ts

### Do's

- **Do** align titles, buttons, and text fields directly to the grid columns when there is no background container color.
- **Do** apply a strict 16dp inset padding when grouping content blocks inside a container with a separate background color or outline stroke.
- **Do** keep buttons at the end of a forms fully enabled, returning focusable validation errors on click, rather than hard-disabling them.
- **Do** enforce a 4dp baseline grid for all text line heights and ensure line heights are divisible by 4.
- **Do** use Google Sans Text for body copy and all font sizes 17pt and below to optimize readability.
- **Do** configure the "Skip to main content" link as the absolute first tab stop in the App Bar.
- **Do** apply a dark outline to chips and text fields to satisfy rigorous Non-Text Contrast (NTC) requirements.
- **Do** use monospaced tabular numbers in data tables or status clocks to maintain optical alignment.
- **Do** add a visible delete "X" icon and set accessibility labels to `Remove [Item]` for input chips.
- **Do** use Anglo-Saxon vocabulary and colloquial contractions (e.g., "don't," "it's") to foster an approachable, conversational tone.

### Don'ts

- **Don't** use a red theme for branding, as red is reserved exclusively for error states and critical negative semantic indicators.
- **Don't** use variable font expressive axes or emphasized type scales in custom layouts; restrict typography to the Static font theme and baseline type scales.
- **Don't** apply shadows or dividers to the App Bar or Navigation elements in their resting, default state.
- **Don't** apply button density by default, ensuring touch targets never contract below the 48x48dp best practice.
- **Don't** stack actionable elements (e.g., never place clickable buttons or text links inside a card that is itself directly actionable).
- **Don't** use ALL CAPS for button labels; always write button text in sentence case.
- **Don't** use "please" followed by a verb (e.g., "Please try again") or modal sandwich adverbs (e.g., "You will now be connected") to avoid creating an cold, impersonal tone.
- **Don't** justify text blocks, as it produces inconsistent letter spacing and degrades readability.
- **Don't** use filled text fields; Outlined text fields are the mandatory recommendation for Elements GM3.
- **Don't** allow page titles to truncate; titles must wrap to multiple lines to remain accessible.
- **Don't** nested more than one layer of cards, and never nested an actionable card inside another actionable card.
